# T009 --- Agent Harness Boundary

## Status

DONE

## Objective

Formalize SOP's provider-agnostic coding-agent boundary so later
workflow stages can ask an agent to perform distinct engineering
capabilities without coupling the orchestrator to one model, CLI,
provider, or harness.

T004 already introduced a minimal generic generation boundary:

``` go
type Agent interface {
    Generate(ctx context.Context, request Request) (Response, error)
}
```

and a subprocess-backed implementation configured by:

``` text
SOP_AGENT_COMMAND
```

T009 should evolve that existing boundary rather than replace it with a
second agent system.

The goal is to make these capabilities explicit:

``` text
DesignTests
Implement
DiagnoseFailure
Fix
Review
```

while keeping provider-specific details outside the orchestrator.

------------------------------------------------------------------------

## Dependencies

-   T003 --- CLI Foundation
-   T004 --- PRD → Plan agent boundary
-   T008 --- Configurable Test Runner

T009 must remain independent of T010 orchestration. It exposes
capabilities; later tasks decide when each capability may run.

------------------------------------------------------------------------

## Architectural Goal

Preserve the core SOP rule:

``` text
Agents do the work.
SOP controls the process.
```

The agent may:

-   reason about requirements;
-   design tests;
-   write implementation instructions or patches;
-   diagnose test/build failures;
-   propose fixes;
-   review code and report findings.

The agent must not own:

-   workflow state;
-   task transitions;
-   branch lifecycle;
-   retry counts;
-   test pass/fail classification;
-   merge decisions;
-   persistence;
-   scheduler decisions.

Conceptually:

``` text
Orchestrator / Task Runner
        │
        ├─ chooses capability
        ├─ supplies bounded context
        ├─ validates result shape
        ▼
      Agent
        │
        ▼
 structured response
        │
        ▼
Orchestrator decides next legal action
```

## Capability Model

Introduce an explicit capability type.

Conceptually:

``` go
type Capability string

const (
    DesignTests     Capability = "DESIGN_TESTS"
    Implement       Capability = "IMPLEMENT"
    DiagnoseFailure Capability = "DIAGNOSE_FAILURE"
    Fix             Capability = "FIX"
    Review          Capability = "REVIEW"
)
```

Exact naming may differ.

Capabilities must be deterministic application values, not free-form
strings generated by a model.

Do not create provider-specific capability names.

------------------------------------------------------------------------

## Request Model

Evolve the request structure so the caller can state what kind of work
is being requested.

A reasonable shape is:

``` go
type Request struct {
    Capability         Capability `json:"capability"`
    Task               string     `json:"task"`
    Input              string     `json:"input"`
    OutputRequirements string     `json:"output_requirements"`
}
```

The planner may continue to use a general capability if introducing one
is useful, or the existing planner request may remain compatible through
an explicit general-generation path.

Do not force planner behavior into one of the coding-specific
capabilities if that makes the model less clear.

A small additional capability such as:

``` text
PLAN
```

or:

``` text
GENERAL
```

is acceptable if needed for backward compatibility.

Avoid a large taxonomy.

------------------------------------------------------------------------

## Agent Interface

The orchestrator must depend on an interface, not `CommandAgent`.

A possible evolution is:

``` go
type Agent interface {
    Execute(ctx context.Context, request Request) (Response, error)
}
```

or retain:

``` go
Generate(...)
```

if adding `Capability` to the request provides enough separation.

Prefer the smallest change that makes capabilities explicit.

Do not add one method per capability unless there is a concrete reason.

This is preferable:

``` text
Agent.Execute(Request{Capability: DesignTests})
Agent.Execute(Request{Capability: Implement})
```

over:

``` go
DesignTests(...)
Implement(...)
DiagnoseFailure(...)
Fix(...)
Review(...)
```

because the latter duplicates transport behavior and makes provider
adapters larger without adding workflow control.

------------------------------------------------------------------------

## Response Model

T009 should give later tasks enough structure to reason about agent
execution without forcing every capability into an elaborate schema.

At minimum preserve:

``` go
type Response struct {
    Content string
}
```

Optionally add lightweight metadata such as:

``` text
provider/harness name
duration
```

only if it is useful and inexpensive.

Do not add token accounting, cost accounting, tracing systems, or
persistence in T009.

Structured capability-specific parsing belongs in the caller when
required by a later task unless a small generic envelope clearly helps.

------------------------------------------------------------------------

## Command Harness Contract

Continue supporting a subprocess-backed provider.

Conceptually:

``` text
SOP
 │
 ├─ JSON request → stdin
 ▼
Configured Agent Harness
 │
 └─ response → stdout
```

Example request:

``` json
{
  "capability": "DESIGN_TESTS",
  "task": "Add repayment calculation",
  "input": "...",
  "output_requirements": "Return test plan and proposed files"
}
```

The configured command remains:

``` text
SOP_AGENT_COMMAND
```

Do not hard-code Claude, Codex, Gemini, Ollama, OpenAI, or any other
provider into core workflow logic.

A user may configure a wrapper for any of them.

------------------------------------------------------------------------

## Command Execution

The current `CommandAgent` uses:

``` go
exec.CommandContext(ctx, "sh", "-c", command)
```

because the harness itself is configured as a trusted command.

Preserve the same explicit trust boundary:

``` text
SOP_AGENT_COMMAND is trusted local configuration.
```

Do not concatenate:

-   task titles;
-   acceptance criteria;
-   model content;
-   test output;
-   PR text;
-   branch names;

into the command string.

Those values belong in the JSON request sent through stdin.

------------------------------------------------------------------------

## Context and Cancellation

Every agent invocation must honor `context.Context`.

Cancellation or deadline expiration must return a distinguishable error.

Do not silently convert context cancellation into a generic provider
failure.

T009 does not define retries.

Later workflow stages own retry policy.

------------------------------------------------------------------------

## stderr Handling

The command harness should:

-   capture stdout as response content;
-   capture stderr separately for diagnostics;
-   include useful stderr details when the command fails;
-   avoid treating stderr output alone as failure if the process exits
    0.

Do not merge stderr into successful agent content.

------------------------------------------------------------------------

## Empty Output

A successful process exit with empty or whitespace-only stdout should be
treated as an error.

An agent invocation that produced no usable response is not a successful
capability execution.

Example:

``` text
process exit 0
stdout ""
    ↓
agent error
```

This prevents later workflow stages from treating missing work as
success.

------------------------------------------------------------------------

## Capability Validation

Reject unknown or empty capabilities before invoking the configured
harness.

Example:

``` text
Capability("")
Capability("DO_ANYTHING")
```

must not execute.

Validation should be deterministic.

If a compatibility/general capability is introduced, it must be
explicitly declared as valid.

------------------------------------------------------------------------

## Input Validation

At minimum validate:

``` text
Capability
Task
```

The exact required fields may vary by capability, but avoid
capability-specific business logic in the transport layer.

For example, the agent package should not know that `DiagnoseFailure`
requires a test runner result object. The caller can serialize the
relevant diagnostic context into `Input`.

Reject obviously unusable requests such as blank task/instruction text.

------------------------------------------------------------------------

## Provider Independence

Core code must not depend on provider-specific request fields such as:

``` text
model
temperature
max_tokens
anthropic_version
openai_response_format
gemini_safety_settings
ollama_keep_alive
```

Provider wrappers may own those details outside the SOP orchestration
contract.

T009's contract is semantic:

``` text
what capability is requested
what task is being performed
what input/context is available
what output is required
```

------------------------------------------------------------------------

## No Filesystem Ownership

The generic `Agent` interface must not directly own repository mutation.

The current package contract says agent implementations must not touch
filesystem or workflow state. Preserve that rule for the generic
boundary.

A later coding harness may internally edit a working tree, but if SOP
chooses to support that mode it must be introduced explicitly with a
controlled adapter and clear lifecycle ownership.

Do not silently change the current `Agent` contract in T009 from:

``` text
content generation
```

to:

``` text
arbitrary repository mutation
```

T010 can decide how generated content or an execution harness is
applied.

------------------------------------------------------------------------

## No Workflow State Mutation

The agent layer must not transition:

``` text
BRANCH_CREATED
TESTS_WRITTEN
RED_VERIFIED
IMPLEMENTING
LOCAL_TESTS_PASS
REVIEW
REVIEW_PASS
FIX_REQUIRED
BLOCKED
```

It returns facts/content.

The orchestrator owns the state machine.

------------------------------------------------------------------------

## Capability Semantics

T009 should document the intended semantic contract for each capability.

### DESIGN_TESTS

Input may include:

``` text
task objective
acceptance criteria
relevant project context
existing tests/code snippets
```

Expected output:

``` text
test strategy
test cases
files/areas likely affected
```

T009 does not execute those tests.

### IMPLEMENT

Input may include:

``` text
task objective
acceptance criteria
test expectations
relevant code context
```

Expected output:

``` text
implementation proposal/content
```

T009 does not decide whether implementation passes.

### DIAGNOSE_FAILURE

Input may include:

``` text
verification category
command
exit code
stdout
stderr
relevant diff/context
```

Expected output:

``` text
likely cause
recommended corrective action
```

The agent must not change PASS/FAIL classification from T008.

### FIX

Input may include:

``` text
task
failure diagnosis
verification output
current implementation context
```

Expected output:

``` text
corrective proposal/content
```

Retry limits are not owned by the agent.

### REVIEW

Input may include:

``` text
acceptance criteria
diff
test results
architecture constraints
```

Expected output:

``` text
findings
severity/reasoning where requested
```

T011 will define the structured self-review policy in more detail.

T009 only establishes the capability boundary.

------------------------------------------------------------------------

## Planner Compatibility

T004 already uses `internal/agent`.

T009 must include regression coverage proving planner behavior remains
valid.

If the request JSON shape changes, update planner tests and
command-agent tests accordingly.

Avoid requiring users to maintain two separate agent commands:

``` text
one for planning
one for implementation
```

unless a future configuration task explicitly adds that capability.

For V1, one `SOP_AGENT_COMMAND` may receive different capability
requests.

------------------------------------------------------------------------

## Tests

Use fake or local subprocess harnesses only.

No network, API key, or model service should be required.

At minimum cover:

### Capability Serialization

Send:

``` text
DESIGN_TESTS
```

and verify the configured harness receives that exact capability in
JSON.

### All Supported Capabilities

Verify the transport accepts:

``` text
DESIGN_TESTS
IMPLEMENT
DIAGNOSE_FAILURE
FIX
REVIEW
```

plus any explicit planner/general capability introduced for
compatibility.

### Unknown Capability

Expected:

``` text
error
harness not invoked
```

### Blank Capability

Expected:

``` text
error
harness not invoked
```

### Blank Task

Expected deterministic validation error.

### Successful Harness

Harness:

``` text
reads JSON stdin
writes response stdout
exit 0
```

Expected:

``` text
response returned
```

### stderr on Success

Harness writes warning/debug information to stderr and valid response to
stdout.

Expected:

``` text
success
response contains stdout only
```

### Harness Failure

Harness exits non-zero and writes stderr.

Expected:

``` text
error contains useful diagnostic
```

### Empty Successful Output

Harness exits 0 with empty stdout.

Expected:

``` text
error
```

### Context Cancellation

Canceled context must stop/abort invocation and return a context-related
error.

### Environment Configuration

Verify:

``` text
SOP_AGENT_COMMAND
```

is primary.

Verify legacy fallback remains supported:

``` text
AGENT_SDLC_AGENT_COMMAND
```

unless the project explicitly decides to remove it in this task.

### Planner Regression

Existing planner tests must continue to pass.

## Optional Fake Agent

A small fake implementation for higher-level tests is useful if kept
simple.

Example:

``` go
type FakeAgent struct {
    Response Response
    Err      error
    Requests []Request
}
```

It may live only in tests.

Do not add a production in-memory provider solely for testing.

------------------------------------------------------------------------

## Error Handling

Errors should identify the failed boundary without exposing unnecessary
input.

Examples:

``` text
invalid agent capability
agent command failed
agent command returned empty output
agent command canceled
```

Do not include the entire prompt/request in errors.

Requests may later contain source code, credentials accidentally
included in context, or sensitive project information.

------------------------------------------------------------------------

## Observability

T009 may expose lightweight metadata or wrap errors with capability
information.

Example:

``` text
agent DESIGN_TESTS failed: ...
```

Do not add:

``` text
database logging
distributed tracing
metrics backend
token usage persistence
```

Those are not required to establish the boundary.

------------------------------------------------------------------------

## Security

Preserve these constraints:

-   agent command comes only from trusted configuration;
-   request data goes through stdin, not command interpolation;
-   no workflow secrets are automatically injected into requests;
-   no full environment dump is returned or logged;
-   no shell command is constructed from agent/model output;
-   no agent-controlled Git command execution is introduced;
-   no agent-controlled state transition is introduced.

------------------------------------------------------------------------

## Acceptance Criteria

T009 is complete when:

1.  the agent boundary explicitly represents engineering capabilities;
2.  `DESIGN_TESTS` is supported;
3.  `IMPLEMENT` is supported;
4.  `DIAGNOSE_FAILURE` is supported;
5.  `FIX` is supported;
6.  `REVIEW` is supported;
7.  unknown capabilities are rejected deterministically;
8.  the orchestrator can depend on a provider-agnostic `Agent`
    interface;
9.  `CommandAgent` remains a valid provider implementation;
10. capability and request data are serialized over the existing stdin
    JSON contract;
11. stdout is returned as agent response content;
12. stderr is preserved for failure diagnostics and not merged into
    successful content;
13. successful empty output is rejected;
14. context cancellation/deadline is preserved;
15. `SOP_AGENT_COMMAND` remains the primary configuration mechanism;
16. provider-specific fields do not leak into core workflow contracts;
17. the agent layer does not own workflow state;
18. the agent layer does not own Git lifecycle;
19. planner/T004 behavior remains working;
20. tests require no network or real model provider;
21. the complete repository suite remains green.

------------------------------------------------------------------------

## Open Code Review

After local verification passes, run Open Code Review against the task
branch.

Review specifically for:

-   duplicate agent abstractions instead of evolving the existing
    package;
-   provider-specific fields leaking into core types;
-   one interface method per capability without clear need;
-   missing capability validation;
-   empty stdout incorrectly accepted as success;
-   stderr merged into successful model content;
-   task/prompt data interpolated into shell command strings;
-   context cancellation reduced to generic failure;
-   planner regression;
-   filesystem or workflow-state ownership moving into the generic agent
    layer;
-   retry policy being implemented in T009;
-   unnecessary model/provider framework complexity.

Fix correctness, compatibility, and security findings.

Decline style-only suggestions that add provider abstractions not
required by the task.

## Definition of Done

T009 is complete when SOP has one clear, tested, provider-agnostic agent
harness that supports the engineering capabilities needed by later
workflow stages, preserves the existing planner integration, uses the
configured command harness through a stable JSON stdin/stdout contract,
validates capability requests deterministically, honors cancellation,
and leaves workflow control entirely to SOP.
