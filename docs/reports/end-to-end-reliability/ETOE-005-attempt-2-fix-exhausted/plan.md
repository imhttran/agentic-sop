# Implementation Plan

## Project

ETOE-005 — Disposable dogfood fixture and deterministic baseline

## Summary

Create a reproducible, disposable SOP dogfood fixture outside any production checkout, containing one success task, one intentionally failing task, and one human-gated task, with expected outcomes and run IDs recorded before execution in docs/reports/end-to-end-reliability/ETOE-005-fixture-baseline.md. The plan first discovers the actual SOP CLI surfaces that the fixture must drive (init, run, task/status/report, retry, human-gate behavior, run-id capture) and confirms which binary to use, then builds the fixture project, records expected outcomes, executes the three tasks, captures run IDs, and records teardown. Per the authoritative plan context, repository discovery targets (such as the installed sop binary vs source build and human-gate/approval CLI surfaces) are discovery work, not external prerequisites; only the Go toolchain required to build the source binary is treated as an externally supplied runtime.

## Assumptions

### The fixture is created and torn down by scripts/documented commands run outside the governed, repository-root-confined harness (i.e. operator-run), with a configurable disposable root.

- Evidence: ETOE-001 §1: internal/toolharness enforces repository-root confinement and rejects `../` escapes; the governed agent therefore cannot create a project outside the agentic-sop checkout. ETOE-001 §8 shows operator-run read-only/outside-harness work is established practice.
- Consequence: The deliverable scripts/documentation must be executable outside the harness and must default to a disposable root (e.g. $TMPDIR/etoe-005-fixture); no stage may implement fixture creation as an in-repo side effect, and the report states this boundary.

### The fixture needs the source-built `sop` binary (from HEAD) rather than the installed binary when a required surface (e.g. `run --max-tasks`, `approval supersede`, human-gate visibility) is missing from the installed one.

- Evidence: ETOE-001 §3: installed binary lacks `run --max-tasks` and `approval supersede`; source build has them. Go toolchain availability confirmed by ETOE-001 §3's successful `go build -o /tmp/sop-preflight ./cmd/sop`.
- Consequence: The discovery stage records which binary the fixture uses and why; the baseline report records the binary provenance (version string and build command) so the baseline is reproducible.

### Run IDs are observable from SOP run artifacts and/or a report/status surface sufficient to be recorded in the baseline report.

- Evidence: ETOE-001 §4/§12 and docs/PLAN.md T032/T039 reference run state, `sop report`, and `.agent-sdlc/runs/<ID>/` artifact directories (e.g. .agent-sdlc/runs/ETOE-001/). The fixture attempt directory docs/reports/end-to-end-reliability/ETOE-005-attempt-1-failure/ shows per-run artifact capture.
- Consequence: Acceptance criterion 3 is satisfiable; the discovery stage pins the exact surface that prints/records the run ID and the capture stage records IDs verbatim.

### A human-gated task can be produced deterministically via an existing SOP mechanism (needs_human outcome per T048, or REQUIRES_APPROVAL command policy per T029, or an approval request), without new SOP features.

- Evidence: docs/PLAN.md T028/T029/T047/T048 list NEEDS_HUMAN/REQUIRES_APPROVAL/needs_human/approval surfaces; docs/reference/CLI.md is the consulted CLI reference. Exact invocation is not yet confirmed (capability: UNKNOWN discovery target).
- Consequence: The discovery stage must confirm the actual human-gate mechanism and binary support before the fixture defines the human-gated task; if no deterministic mechanism exists, the stage records the gap and the fixture uses the closest supported placeholder contract rather than inventing new SOP behavior.

### The intentionally failing task fails through SOP's deterministic validation/quality gate (not through model interpretation), so the baseline's expected FAIL outcome is reproducible.

- Evidence: docs/PLAN.md Stage 8 (deterministic pass/fail classification) and T028 (deterministic quality gate PASS/FAIL/NEEDS_HUMAN); `sop validate` (T030) is a validation runner.
- Consequence: The failing task is written to violate a declared validation (e.g. a failing test or an unmet validation command), and its expected outcome (validation FAIL / run outcome) is recorded before execution.

### The prior failed attempt at docs/reports/end-to-end-reliability/ETOE-005-attempt-1-failure/ is evidence to consult, not to be modified or reverted.

- Evidence: The directory contains attempt artifacts (task.md, activity.jsonl, state.json, etc.); SOP records attempts append-style under .agent-sdlc/runs/<ID>/ per ETOE-001 §4.
- Consequence: The plan's stages read attempt-1 artifacts for lessons but do not modify them; the new deliverable is a separate file (ETOE-005-fixture-baseline.md) and new fixture runs create new run IDs.

### The fixture project can be defined entirely from files (PRD/PLAN/tasks/validation config) plus SOP CLI invocations, without depending on GitHub, remote CI, or external services.

- Evidence: docs/PLAN.md T042 (local vs remote completion, LOCAL_DONE) and T043 (bootstrap independent of agent); the ETOE-005 acceptance criteria require only a disposable initialized SOP project and local runs.
- Consequence: The fixture stays local and deterministic; remote adapters (GitHub) are out of scope and not depended on.

## ETOE-005-S1 — Fixture project definition and deterministic setup/teardown scripts

Author the disposable fixture project and its reproducible lifecycle. Define the fixture root as a configurable directory outside any production checkout (default a temp location such as $TMPDIR/etoe-005-fixture). Provide setup that (1) creates the fixture root, (2) runs `sop init` there to produce an initialized SOP project, and (3) writes the fixture's project inputs using only surfaces confirmed in ETOE-005-S0: a PRD/PLAN (or task files) containing exactly one success task, one intentionally failing task (failing via the deterministic validation/quality gate), and one human-gated task against the confirmed gate mechanism. Provide teardown that removes only the fixture root and reports whether removal succeeded. Scripts must be idempotent (re-running setup on an existing fixture root is either rejected with a clear message or cleanly re-created) and must never write inside the agentic-sop checkout. Include the expected outcomes for all three tasks in the fixture definition itself (success ⇒ completed/LOCAL_DONE-class outcome; failing ⇒ validation FAIL class outcome; human-gated ⇒ gate outcome) so outcomes are declared before execution.

### Dependencies

- ETOE-005-S0

### Requires

- Go toolchain for building the source `sop` binary

### Deliverables

- Reproducible fixture setup script (e.g. scripts/etoe-005-fixture-setup.sh) taking a configurable fixture root and binary path.
- Reproducible fixture teardown script (e.g. scripts/etoe-005-fixture-teardown.sh) removing only the fixture root.
- Fixture project inputs (PRD/PLAN/task files and any validation/quality-gate configuration) containing the success, intentionally failing, and human-gated tasks with their expected outcomes declared.

### Acceptance Criteria

- Running setup creates a disposable, `sop init`-initialized SOP project at a configurable path outside any production checkout, and running setup twice behaves per the documented idempotency rule.
- The fixture contains exactly three tasks: one success task, one intentionally failing task, and one human-gated task, each with a written expected outcome recorded before any execution.
- The intentionally failing task fails through the deterministic validation/quality gate, not model interpretation.
- Teardown removes only the fixture root and leaves the agentic-sop checkout and `.agent-sdlc/` state unmodified.
- Scripts contain no absolute production-checkout paths; the fixture root is the only mutated external location.

## ETOE-005-S2 — Baseline execution: run the three fixture tasks and capture run IDs

Execute the fixture using the setup produced in ETOE-005-S1 and the surfaces pinned in ETOE-005-S0: run the success task to its expected completion-class outcome, run the intentionally failing task to its expected validation-FAIL-class outcome, and run or reach the human-gated task to its expected gate outcome (needs_human/approval request as confirmed). Capture for each run: the run ID from the confirmed surface, the observed outcome, and where the outcome was observed (status/report output or `.agent-sdlc/runs/<ID>/` artifacts). Do not modify the fixture's declared expected outcomes after observing results; where observation differs, record the discrepancy as a finding rather than editing the expectation. Then run teardown and record that the fixture root was removed.

### Dependencies

- ETOE-005-S1

### Deliverables

- A capture record of the three runs: input task, run ID, observed outcome, and observation surface.
- Teardown execution record showing the fixture root removed.

### Acceptance Criteria

- All three fixture tasks are executed and each produces a recorded run ID from the surface pinned in ETOE-005-S0.
- The success task's observed outcome matches its predeclared expected outcome, or the mismatch is recorded as an explicit finding.
- The intentionally failing task's observed outcome is a validation-FAIL-class result matching its predeclared expected outcome, or the mismatch is recorded as an explicit finding.
- The human-gated task reaches the confirmed gate outcome (needs_human/approval request) matching its predeclared expected outcome, or the mismatch is recorded as an explicit finding.
- Teardown removes the fixture root and the agentic-sop checkout and `.agent-sdlc/` state remain unmodified.
