Date: 2026-11-21
Status: **Draft, unreviewed.** Generated by `sop prompt --capability plan` (model `deepseek-v4.1-flash:cloud`), read-only. It is not an approved plan and authorizes no implementation. The model did not re-read `drive.go`, `resume.go` or all of `prompt.go`, so those claims are unverified.

## Assumptions

- The task Input's citations (run.go:199, drive.go:83) are accurate for lease acquisition sites; drive.go was not re-read in this session.
- A start launched by startWork runs `sop prompt --capability C --file P` or `sop run PLAN` as a detached child through launchWorkProcess, so the child executes exactly one of prompt.go/run.go and can acquire the lease there.
- `sop prompt` (prompt.go) runs the whole governed request in one process with no further child; it was not re-read in full this session, so the acquire point is chosen at the top of the command handler.
- BusyError maps to an operator-actionable message without code change; the existing acpStartWorkResult mapping already turns a busy doc into WorkOutcomeBusy, so only startWork needs the check.
- Tests can inject env.launch, env.alive, env.stop, env.now (workEnv) plus deps seams to stay deterministic with no model and no network.
- planflow and approval take projectlock (state.lock) inside their own operations; no call path takes state.lock and then an execution lease, so execution-lease-before-metadata ordering is achievable by taking the lease first in each execution entry point.
- execution.lease off must remain a strict no-op: executionLease returns (nil, nil) under off, and any new check must short-circuit before touching the lease file.

### 1. Dropped: lease-inheritance helper

Built by an earlier SOP run (an `InheritEnv` marker, `InheritedOwner`, `leaseAcquireOrInherit`), reviewed, and dropped before any commit. Under child-as-acquirer no parent holds a lease for a child, so nothing would set the marker and the helper would have no caller. ### 2. Wire the execution lease into `sop prompt` (proposal step 2 completion)

### 4. Let the child acquire the lease itself and close the handshake window

**Changes**

- Decided (DESIGN-DECISIONS D1): the child process is the sole acquirer; the parent writes no lease and sets no marker. The child writes Owner.JobID from JobEnvID, so the parent can tell which child owns the lease.
- Document the window: startWork releases the start lock after cmd.Start(); the child may take up to a bounded time to reach lease acquisition. startWork therefore cannot report 'started' as proof of exclusion. Under required, startWork must either (a) wait a bounded interval for state.exec.lock to appear with the child's job id and report started only then, or (b) report started with a 'lease_pending' flag. Pick (a) with a documented constant (proposed workLeaseHandshake=2s) and fall back to (b) on timeout.
- Close the window for concurrent CLI runs with the same ordering: because the lease is created by the child with O_EXCL, a CLI `sop run` arriving in the window acquires the lease first and the child then fails fast with a BusyError, which is reported in the job log and as the job's exit; the child must never silently run without the lease in required mode.

- internal/cli/acp.go (no change expected)

**Tests**

**Done when:** A started job is either confirmed lease owner or explicitly reported lease-pending; no path reports started as proof of exclusion.

## Open questions

- **Heartbeat failure on a live run.** execution_lease.go prints to stderr and continues. Under required, a holder whose heartbeat fails (cross-host, or Windows) still blocks other starts until HeartbeatLimit elapses, and then a second execution may start while the first is alive. Decide: (a) keep current 'report and continue' (proposal §4), (b) fail the run closed on a lost lease, or (c) add a host-local pid re-check before treating a cross-host lease as stale.
- **Stale detection across hosts.** State.Stale trusts the heartbeat for a foreign host. A live remote run whose heartbeat stalls for >5m looks stale and `sop resume` could release it. Decide whether release across hosts must require an operator confirmation flag, and whether NFS/shared-checkout projects are in scope.
- **SIGKILLed child leaves an orphaned lease.** The lease is a file. If the child is SIGKILLed the file survives with a dead pid. Same-host staleness is detected by pid liveness and `sop resume` releases it, but no process runs the release automatically. Decide whether `sop run`/startWork should surface the stale hint and require `sop resume`, or offer a documented `sop lease release --stale` operator command.
- **Handshake window design.** Step 4 chooses between (a) a bounded wait in startWork for the child to acquire the lease, and (b) an explicit lease_pending flag. Both are deterministic; (a) changes the 'started' contract latency. Decide the constant and the contract wording.
- **Inheritance marker vs re-entrant acquire.** Resolved by DESIGN-DECISIONS D1: child-as-acquirer, single writer, no marker.
- **acpBusyProbeTimeout and the metadata probe.** acp.go's LockTaker still probes and releases projectlock. Decide whether the probe stays (cheap pre-check) once the lease is authoritative, or is removed to keep a single 'busy' reason.
- **Prompt process model.** Assumption held that `sop prompt` runs the whole request in one process. If it spawns a further child, the lease must move to that child. Confirm during implementation of step 2.
- **drive.go graph-mode detail.** drive.go was not re-read in this session; the lease call at drive.go:83 and the runGraph function are taken from the task Input and gap record. Confirm before step 7 that the graph path defers Release and that the owner TaskID is the graph task or empty.
